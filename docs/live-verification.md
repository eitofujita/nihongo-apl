## 変更を行わない自動接続確認

アプリを起動した状態で実行します。`.env.local`の公開接続情報とアプリURLを使います。

```bash
npm run test:live
```

このコマンドはアカウント作成、メール送信、学習履歴の変更を行いません。実Authの設定、匿名アクセス拒否、ローカルAPIの認証・CSRF保護、コールバックの戻り先を確認します。通常の`npm test`では実接続テストをスキップします。

## 本人が行う操作

1. アプリへ登録し、同じブラウザで確認メールのリンクを開く。すでに登録済みならログインから始める。登録直後は確認待ち画面、認証後はホームへ移動することを確認する。
2. 「Meet は and です」のレッスンを最後まで解き、保存完了を確認する。履歴の件数と得点を控える（初回の例：1件・3問中の正解数）。間違えた問題は復習キューにも入る。
3. 履歴画面を再読み込みし、件数・得点が維持されることを確認する。
4. ログアウトして同じアカウントで再ログインし、履歴が維持されることを確認する。
5. 別ブラウザでも同じアカウントでログインし、同じ履歴を確認する。言語を切り替えても同じ履歴が表示されることを確認する。
6. 別のテスト用アカウントBでログインし、Aの履歴・設定が表示されないことを確認する。Bを新規作成する場合はメール配信先の制限に注意する。
7. 自分の受信可能なメールでパスワード再設定を行い、新しいパスワードでログインできることを確認する。パスワードは記録・共有しない。

画面上の保存成功表示だけでなく、再ログイン後・別ブラウザでの読込で保存を確認します。既存の学習履歴を削除するリセット操作は、この確認には不要です。

結果を共有する際は「どの操作まで進んだか」「履歴の件数・得点」「表示されたエラー」だけで十分です。秘密情報の共有は不要です。

## メールを増やさずDBの分離を確認する

`supabase/verify.sql`の全文をSupabase SQL Editorの新規クエリに貼り、postgresロールで実行します。これは初期セットアップ済みのDB向けの検証です。`setup.sql`を再実行する手順ではありません。

2つのランダムな一時ユーザーを使い、`authenticated`ロールとユーザーIDを切り替えて5テーブルの分離、他人の設定更新の拒否、DB側採点、重複防止、本人だけのリセットを確認します。既存ユーザーはテスト対象にせず、メール・パスワード・有料権限の発行も行いません。成功時の最終結果は`PASS: account isolation, grading, retries and scoped reset. Test data rolled back.`です。

末尾は`ROLLBACK`で、一時ユーザー・履歴・設定の変更を取り消します。実行エラーの場合もコミットせず、`ROLLBACK;`を実行してから結果を確認します。`ROLLBACK`を`COMMIT`に変更しないでください。これは[Supabase公式のRLSテスト](https://supabase.com/docs/guides/database/postgres/testing-row-level-security)と同じくDB内で権限・IDを再現する検証で、実JWTによるログインやメール配信のテストではありません。

検証SQLの追加後、型チェック・Lint・通常テスト84件が成功しています。検証SQLを既存データがあるローカルPostgreSQLで2回実行し、既存ユーザー・プロフィール・履歴件数と既存ユーザーの結果が維持されることを確認しました。RLSを無効化した場合、過剰な読取ポリシーを追加した場合の異常検出も確認済みです。実Supabaseでの実行結果はまだ確認していません。

## 再設定メールの429

`POST /api/auth/recover`の429は、メール申請の回数制限です。アプリの制限（3回／分）と認証サービスの制限は別です。[Supabase公式の制限](https://supabase.com/docs/guides/auth/rate-limits)では、標準メール配信はプロジェクト全体で2通／時、同じユーザーへの再設定要求は通常60秒間隔です。実プロジェクトの設定や独自SMTPの有無は、管理画面のAuth設定で確認します。既存の429ログだけから、どの制限かや解除時刻は断定できません。

アプリはローカル制限を`rate_limit`と`Retry-After`、Supabaseのメール制限を`email_rate_limit`、その他のSupabase制限を`auth_provider_rate_limit`として区別します。サーバーログは制限種別だけで、メールアドレス・パスワード・認証コード・プロバイダーのエラー全文を出力しません。

画面は送信成功後60秒間と429発生時に再送を抑止します。ローカルの`Retry-After`を優先し、不明時は60秒の再試行待機を表示します。この60秒はSupabase側の制限解除を保証せず、自動再送もしません。Supabaseの制限自体は変更・解除していません。再設定APIはモックで検証し、追加の実メールは送っていません。

修正後の確認：型チェック・Lint・通常テスト88件、関連ブラウザテスト10件が成功。新しいパスワードでの実ログイン確認は未完了です。

## 再送失敗後に先のメールを使えなくなる問題への対応

公式SDKを実際に使い、外部HTTPだけを模擬したテストで「最初の再設定要求が成功→次の要求が429→先のメールのコードを交換」が失敗することを再現しました。サーバー側がメールごとのフローIDを扱わず、最後の申請用の検証情報だけを使っていたためです。

修正後はSDKが各メールへ`sb_flow_id`を付け、コールバックで形式を検証してそのメールの検証情報を指定します。上記の再現テストが成功し、認証Cookieを引き継いだ`POST /api/auth/password`による変更要求まで通ることを確認しました。存在しないフローや検証情報のないブラウザでは、コード交換を試みずエラー画面へ戻します。

これはアプリ側の認証処理の修正で、Supabaseの送信制限の解除や、本人が報告したネットワーク接続エラーの解消を確認したものではありません。実メールは追加送信していません。次の実メール確認は、制限解除後に修正を適用した画面から新たに申請し、同じブラウザで行います。
